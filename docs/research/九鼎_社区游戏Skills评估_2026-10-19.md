# 九鼎：社区游戏 Skills 适配评估

调研日期：2026-10-19。范围为来源核对、原文审读、公开社区反馈与项目适配判断；未安装候选 Skill、运行候选脚本或开展游戏效果对照实验。本文是建议，不修改项目架构、玩法或迁移验收要求。

**结论：不建议整套安装题列六项。近期优先试用任务明确的 Godot 脚本、场景和无头测试 Skill；`game-feel` 用于受约束的小样；UI 采用设计清单与 Godot 原生实现指导分工；设计理论按需咨询。浏览器建站、Unity／Unreal 开发 Skill 不适合作为当前主开发入口。**

## 1. 项目基线与评估方法

判断依据为当前工作区的[架构结论](../architecture/九鼎_架构选型结论.md)、[玩法规则](../product/十日_玩法与运行规则.md)、[术语表](../../GLOSSARY.md)、[ADR-0010](../adr/0010-godot-migration-direction.md)及[迁移方案 Q1—Q9](../architecture/九鼎_Godot架构评估与迁移落地方案_2026-10-19.md)：

- 后续方向是 Godot 原生 2D、带类型 GDScript；当前实际运行工程仍是 Electron／Phaser，须保留作对照。
- 皮影／手绘精灵、固定等距观感、二维战斗平面、离线图集；不借技能引入真实 3D、骨骼运行时或新 ECS。
- 先保持汤谷规则、数值、碰撞和操作中断行为等价；动态小样经用户试玩确认后扩展。
- Windows x64 与 Apple Silicon Mac 原生验收；构建、无头规则测试、单平台通过均不能代替双平台实机证据。
- 首个迁移交付以键鼠为范围；手柄、正式肉鸽闭环、存档、Steam 完整功能后续实施。

用户提供的是名称和能力简介，没有仓库地址。本文选择可查到的代表实现，同时列出重要同名差异，**不把同名技能当成同一产品**。适配判断均是结合上述项目约束的推断。

检索顺序为 skills.sh 榜单、`npx skills find godot`、源仓库 `SKILL.md`／参考文件、GitHub issue／PR。证据分开处理：

| 证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| Skill 原文与脚本 | 实际任务、默认值、依赖和实现方式 | 实际生成结果一定正确 |
| 有具体复现与修复的 issue／PR | 某个问题被报告、复核或修正 | 整个合集所有技能成熟 |
| 作者展示、验证声明 | 作者执行过所述工作 | 独立评测、对本项目有效 |
| 安装数、仓库星标 | 传播与采用线索 | 游戏更好玩、帧率更高、无缺陷 |

本次没有找到题列六项统一、可复现的独立效果基准。“未检索到反馈”表示本次检索的证据缺口，不代表没有用户、没有问题或没有价值。

## 2. 题列六项的结论

| Skill／本次核对来源 | 对九鼎有用的部分 | 主要不匹配 | 建议 |
| --- | --- | --- | --- |
| [`higgsfield-websites` · higgsfield-ai/skills][higgs] | 素材风格、精灵／音频生产参考，另做网页演示时有用 | React／TanStack／Cloudflare 与平台模板；不是 Godot 桌面生产链 | **当前不引入完整工作流** |
| [`game-engine` · github/awesome-copilot][engine] | 输入—更新—渲染、碰撞和网页小游戏示例 | 主体为 HTML5／Canvas／WebGL／JavaScript；现有 Phaser 已承载循环 | **旧工程按需参考，Godot 迁移不主用** |
| [`game-developer` · Jeffallan/claude-skills][developer] | 测量后优化、状态机、跨平台检查意识 | Unity／Unreal API、工具与强制 LOD／池化倾向 | **当前不采用为实现技能** |
| [`game-ui-design` · 多来源，见下文][ui-jeremy] | HUD 可读性、状态完整性、玩家决策、暂停／阅读交互 | 同名差异大；部分默认 controller-first 或偏手游运营 | **设计清单可用，原生实现优先 Godot UI Skill** |
| [`game-design-theory` · jarrodmedrano 等][design-jarrod] | 教学、难度、公平感、节奏与试玩问题整理 | 理论不等于验证；不能迁移时重设计既定规则 | **后续按需咨询，暂不常驻** |
| [`game-feel` · gamedev-skills 等][feel] | 命中可读性、视听反馈、逐层对照调校 | 全局停顿、输入缓存、惯性等可能改变现有行为 | **六项中近期最值得受约束试用** |

### 2.1 higgsfield-websites：能力存在，整条流程不匹配

原文确实含游戏素材引用，但游戏开发路径绑定浏览器模板与平台生命周期。素材生产能力不能据此推导为适合原生桌面工程。还有“不查看自己生成的结果”等指令，与本项目实际画面验收要求冲突；不能照单执行。[原文][higgs]

社区发现具体兼容性报告：用户报告官方技能 frontmatter 无法通过当前 Codex 验证，修复 PR #12 在本次查询时仍开放。这是报告及提案，**本次未在本机复现加载失败**；也不能把格式修复等同于 Godot 兼容。[issue #80][higgs-80]、[PR #12][higgs-12]

若未来单独试验其美术能力，应先用一个资产验证视角、透明边缘、脚点、方向一致性与游戏内观感；当前已有 `imagegen` 可用，不必为了生成一张精灵引入建站、账号和部署流程。

### 2.2 game-engine：有网页演示证据，不是 Godot 工程方案

该 Skill 的循环示例使用 `requestAnimationFrame`，模板主要为网页游戏。对旧版理解碰撞与输入有帮助，但迁移时再搭一层 JS 游戏循环没有收益，也不应升级 Phaser 或引入浏览器多人系统。[原文][engine]

其引入 PR #792 提供一次 Claude Sonnet 4.6、单提示词、无后续编辑的网页清版动作游戏演示，并链接支持仓库。这比只有能力清单更具体，但仍是贡献者自报的示例，未证明 Godot、长期维护或双平台原生表现。[PR #792][engine-792]

### 2.3 game-developer：工程意识可借鉴，默认实现会带偏

其验证工具指定 Unity Profiler／Unreal Insights，参考实现使用 MonoBehaviour、Actor 等；约束要求池化、LOD 等。九鼎当前需要保持已有小步进碰撞语义，不是借迁移重建 Unity 式组件体系，也不应在没有瓶颈证据时补这些优化。[原文][developer]

外部贡献者的 PR #172 改进过其验证检查点，并展示 `tessl skill review` 的 74%→100% 评分。这个数字是技能文档审查结果，**不是游戏成功率、性能或好玩程度**。更早 issue #41 虽提到 Godot，当前实际引用文件仍以 Unity／Unreal 为主，应以现在内容为准。[PR #172][developer-172]、[issue #41][developer-41]

### 2.4 game-ui-design：适合评审，但要拆开设计与引擎实现

| 同名实现 | 审读发现 | 处理方式 |
| --- | --- | --- |
| [omer-metin/skills-for-antigravity][ui-omer] | controller-first；依赖 patterns／sharp_edges／validations，部分 Unity 示例 | 可参考可读性和焦点清单；不得扩大首期手柄范围 |
| [jeremylongworth-source/AgentSkills][ui-jeremy] | 从即时决策、状态、信号、动态画面验证出发 | 内容更贴合 HUD 状态评审；低采用度，列为试验性参考 |
| [Game-UI-Extension][ui-extension] | 屏幕地图与规格产物，含商城、活动等运营语境 | 当前不选；不能据此新增运营系统 |

本次未检索到这些具体 UI Skill 的独立游戏效果对照；omer 仓库说明由 Vibeship 内容转换，转换过程不是效果认证。jeremylongworth 仓库在 API 快照中仅 1 星，不能推荐成成熟依赖。[来源说明][ui-omer-origin]、[jeremylongworth 仓库][ui-jeremy-repo]

实际使用建议：设计层审核血量、技能冷却、暂停、残碑阅读，以及正式系统实施时的一炷香显示；实现层由下文 `godot-ui-control` 负责 Control／Container／Theme。正式计时与结算未进入当前交付，不因 UI 清单新增系统。

### 2.5 game-design-theory：有咨询价值，缺少效果证据

jarrodmedrano 版本基于 Richard Rouse III 理论，明确不编程；适合把“无聊／不公平／不知往哪走”转成试玩假设。另一个 [pluginagentmarketplace 版本][design-plugin] 是 MDA、flow、奖励和平衡概览；其额外元数据不能证明已有自动评测器。[jarrod 原文][design-jarrod]

未检索到两份技能的独立调校结果。jarrod 仓库 API 快照为 2 星、`license: null`，表示本次 API 未识别许可证，**不是已经证明没有许可证**；直接引入或分发前需核对原仓库授权。因此目前建议阅读方法、按需咨询，暂不列安装优先项。[仓库][jarrod-repo]

迁移时保持数值；正式肉鸽设计阶段再用它审核局内选择、探索支路收益、叙事证据与重复游玩节奏。输出应是观察、假设、验证方法，不直接把通用理论改写为项目规则。

### 2.6 game-feel：最贴近当前需求，仍须审查具体配方

gamedev-skills 版本强调在已有机制上叠加反馈，提供 Godot 震动、Tween 和停顿示例。其 hit-stop 代码直接修改 `Engine.time_scale` 并恢复为 `1.0`；据代码审读可推断，它没有完整处理重叠停顿和既有缩放状态。**这是未运行的审读发现，不能直接复制到项目时间管理中。**[原文][feel]

其他同名版本：jarrod 的侧重点是 Swink 理论咨询；[ronniebasak][feel-ronnie] 更强调测量与调校，但同时要求大量参数热更新等。后者 API 快照仅 1 星，本次未找到独立使用结果。三者不可凭名称互换。

建议从普通箭命中一个影偶开始，比较命中部位辨识、飘字与实际伤害对应、音效层次和皮影轮廓。不要同时修改伤害、冷却、击退、相机与全局时间。输入缓存、停顿及震屏须与暂停／失焦／重试规则共同验证，且变化需用户试玩确认。

## 3. 社区反馈最有分量的正反证据

### 3.1 对大合集的质疑成立，但不能据此否定每一项

gamedev-skills 的外部 issue #2 批评内容过宽、更像上下文库；维护者承认扩展到部分不熟悉引擎时大量借助 AI，不能对所有内容提供同等保证，并认可收窄任务和补验证的方向。讨论后 issue 已关闭，**关闭不等于全库已经完成实测**。[讨论与维护者回应][community-2]

正面是后续 PR #17 明确记录修正来源和哪些仅核对文档、哪些实际跑过。应把它看作维护与透明度信号，而不是商业游戏质量保证。[PR #17][community-17]

### 3.2 无头测试 Skill 有更具体的复核闭环

PR #16 中，提交者明确披露由 AI agent 提交；维护者随后报告在 Godot 4.7.2 Linux 上复核，发现新检出项目缺导入步骤、裸 `assert()` 可能挂起、部分示例永远返回成功及异步初始化问题，并推进修正合并。其价值在于可复现的行为与修复，不能仅因 AI 参与否定或认可。[PR #16][testing-16]

这在本轮候选中属于较强的任务级证据，但覆盖的是上游所述环境；本项目尚未运行，仍需在锁定引擎与两端工程复核。无头测试验证规则，不验证画面、音频、输入延迟或用户手感。

## 4. 进一步检索：更适合的候选

前七项来自同一 [gamedev-skills 仓库][gamedev-repo]，每项只按任务加载，不建议安装整个多引擎合集。其版本说明明确：新项目基线不是对现有项目的强制升级要求。[版本政策][gamedev-version]

| 优先级 | 具体 Skill | 对九鼎的实际任务 | 限制／验收点 |
| --- | --- | --- | --- |
| **优先试用** | [`godot-gdscript`][gdscript] | 带类型脚本、生命周期、`@export`／`@onready`、信号语法 | 按项目锁定版本核对；不能替代规则对照测试 |
| **优先试用** | [`godot-nodes-scenes`][scenes] | 可复用角色／敌人／交互物场景，编辑器调整布局 | 保留纯规则边界；不能把战斗状态全部放进 Autoload |
| **优先试用** | [`godot-gdscript-headless-testing`][testing] | 移植既有 TS 规则用例，确保失败能阻断 CI | 此项有上述具体 PR 复核；仍需本机验证 |
| **做 UI 时加载** | [`godot-ui-control`][godot-ui] | 将 DOM HUD 转为 Control、Container、Theme，处理缩放和点击穿透 | 不擅自加入手柄交付；不承诺独特美术风格 |
| **做资产时试用** | [`create-game-assets`][assets] | 风格参照、资产清单、透明通道、尺寸、锚点、游戏内验证 | 它管理生产与 QA，不自带图像模型；复用已有图集基线 |
| **做动画时加载** | [`godot-animation`][animation] | SpriteFrames／AnimatedSprite2D、AnimationPlayer、Tween | 不为简单精灵强加 AnimationTree；动画不能重新裁决伤害时刻 |
| **做原生包时加载** | [`godot-export`][export] | 匹配导出模板、资源包含规则、Windows／Mac 构建入口 | 打出文件不代表双平台已验收；平台细节回查官方文档 |
| **替代，二选一** | [`godot-gdscript-patterns` · wshobson/agents][wsh-patterns] | 信号、状态机、Resource 的较完整参考 | 热度较高；示例的 CharacterBody2D 移动和全局状态不能代替迁移既定方案 |
| **后置观察** | [`godot-playtest-and-debug` 等 · hybridindie/godot-mcp][mcp-skills] | 通过编辑器工具运行、查看场景和调试 | Skill 不等于 MCP；需要额外服务／插件。小样初期 CLI＋人工试玩更简单 |

`create-game-assets` 有资产报告和预览脚本、风格与来源清单，并要求原生比例和游戏内检查。这比“生成漂亮图片”更接近九鼎的素材接入问题；本次只读其脚本，未运行，亦未检索到证明其提升成品美术质量的独立对照。[Skill][assets]、[资产检查脚本][asset-script]、[相关整合 PR #9][assets-9]

`wshobson` 是合理备选，不建议与另一套通用 GDScript 架构指导同时常驻；本次源仓库按 `godot` 搜索命中的主要是跨工具适配 PR，没有找到该具体技能的独立游戏评测。它的热门程度不足以推翻九鼎已确认的“先等价移植规则、再单独评估引擎物理”的决定。[Skill 与详细模式][wsh-patterns]、[详细参考][wsh-details]

MCP 候选有工作流价值，但不能因能截屏就自动得到画面正确性。其上游还存在最低版本 e2e 覆盖等跟进项，因此这里只列后置观察，不纳入首轮必装。[技能说明][mcp-skills]、[上游测试跟进 #701][mcp-701]

未优先推荐 Godot 的移动／物理通用模板，是因为本项目必须先保留已有移动、线段接触、击退、操作中断语义；这不是认为引擎原生物理不好。未推荐多人、C#、Unity／Unreal 或完整 Steam 发布技能，是当前范围和语言不匹配。场景组织和 CLI 行为最终回查 [Godot 官方场景组织文档][official-scenes]与[命令行文档][official-cli]。

## 5. 建议的最小采用与验证顺序

**第一轮只考虑三个：`godot-gdscript`、`godot-nodes-scenes`、`godot-gdscript-headless-testing`。** 先在迁移工作开始时用实际小任务验证增益；无需先扩建技能体系。题列 `game-feel` 在需要评审小样手感时按需调用，UI／素材／动画／导出各到任务阶段再加载。

| 顺序 | 试用任务 | 成功标准 |
| --- | --- | --- |
| 1 | 用相同输入夹具移植规则与操作中断 | 生命、伤害次数、阶段、事件严格对应；位置允许事先明确容差；故意让断言失败时进程返回非零 |
| 2 | 创建角色、一个影偶、遮挡物和镜头小样 | 用户能在编辑器调位置再试玩；场景可重用；没有重复运动／伤害裁决 |
| 3 | 只对一个普通箭命中事件试验反馈 | 同规则 A/B 录像可比较；不补发中断前攻击、不改变冷却或敌人预警；用户试玩确认 |
| 4 | 接 HUD 与代表素材 | 目标比例和动态下可读；点击不被装饰层吞掉；脚点、方向、透明边缘和图集稳定 |
| 5 | 导出与平台验证 | 按迁移方案登记两端设备、原生操作、60 秒帧时间及 5 分钟稳定性证据；不混淆测试层次 |

每次试用至少记录：具体来源版本、任务、产生的改动、发现的错误、修复轮次及验收结果。若技能只重复常识、带来范围外改动或增加返工，就停用该项。上下文和冲突指令的成本应与实际节省的工作比较，而不是与技能数量比较。
