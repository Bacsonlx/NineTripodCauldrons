# 九鼎 Godot 迁移规格：汤谷等价切片与双平台交付

2026-10-19。依据迁移访谈 Q1—Q9、ADR-0010 及本轮确认的测试边界编制。范围为迁移方案的 M0—M4；发布规格时，游戏代码仍运行 Electron／Phaser，Godot 工程尚未建立。

## Problem Statement

九鼎计划以二维手绘／精灵、固定俯视或等距视角制作 PC／Steam 单机动作肉鸽游戏。现有汤谷切片已经具备战斗、探索和部分行为测试，但关卡、图集、动画、输入与桌面交付分散在代码和网页容器工具链中，不便于用户直接调整场景并试玩。

用户已经决定迁移到 Godot，希望保留已经确认的操作、战斗与探索规则，并形成“用户在编辑器调整与验收，AI 负责脚本和批量配置”的制作方式。迁移需要提供能实际试玩、可编辑、在指定 Windows 与 Mac 上通过验收的汤谷，而不是只有新引擎工程壳或一份代码翻译。

当前没有 Godot 性能或兼容性实测。现有规则测试、构建成功与历史浏览器证据不能代替新版本的原生双平台验收；旧 MVP 未完成的验收继续独立保留。

## Solution

采用 Godot 原生 2D、带类型的 GDScript 和既有离线图集，分阶段迁移当前汤谷。先固定可还原的旧版参照、规则用例与资产清单，建立可导出的双平台最小工程，再交付包含移动、独立瞄准、普通射箭、一个影偶、一个遮挡物与跟随镜头的真实动态小样。用户实际试玩确认画面和手感后，继续完成三组战斗、全部现有技能、两条支路、残碑、祭坛、捷径、反馈和 HUD。

用户能够在 Godot 编辑器调整道路、障碍、敌人出生点和互动点，保存后重新打开或立即试玩，实际可走范围与阻挡随布局一致变化，无需修改战斗源码。最终提供 Windows x64 与 macOS arm64 可运行产物及各自验证记录。

Godot 方向已确定，验收决定主入口切换时点。质量或兼容问题先修复，旧工程在过渡期作为参照和临时运行入口保留。手柄、正式肉鸽闭环、存档和 Steam 完整功能进入后续规格。

## User Stories

1. 作为玩家，我希望在 Windows x64 上解压并启动汤谷，以便直接体验迁移版本。
2. 作为玩家，我希望在 Apple Silicon Mac 上解压并启动汤谷，以便获得对应平台的原生体验。
3. 作为玩家，我希望离线启动并游玩，以便本次切片不依赖 Steam 客户端或网络。
4. 作为玩家，我希望通过 WASD 移动且斜向不额外加速，以便保持现有移动手感。
5. 作为玩家，我希望移动与鼠标瞄准分离，以便在移动中攻击任意方向。
6. 作为玩家，我希望短按左键能完成一次有效射箭、按住能连射，以便保留两种攻击操作。
7. 作为玩家，我希望箭从可见握点沿瞄准方向射出，以便画面与弹道对应。
8. 作为玩家，我希望箭先命中路径上最早接触的目标或实体，以便不会隔墙命中后方对象。
9. 作为玩家，我希望 Q 穿透箭可贯穿同一路径多个影偶且对每个目标只伤害一次，以便技能行为可靠。
10. 作为玩家，我希望 E 箭雨固定在确认的合法落点并分段生效，以便预警、范围和伤害一致。
11. 作为玩家，我希望非法箭雨落点给出反馈且不消耗冷却，以便理解未能释放的原因。
12. 作为玩家，我希望通过空格闪避并保留既有位移、无敌和冷却规则，以便能按熟悉的节奏避开攻击。
13. 作为玩家，我希望影偶正常激活、追击、预警、挥击、恢复和死亡，以便战斗威胁可读且可应对。
14. 作为玩家，我希望受击、实际伤害、击退和飘字对应，以便辨别攻击是否命中。
15. 作为玩家，我希望击退在墙、关门和地图边界停止，以便角色不会被推出合法空间。
16. 作为玩家，我希望致死攻击只报告实际扣除生命，重复读取状态不重播同一命中，以便反馈可信。
17. 作为玩家，我希望依次完成三组 3／4／5 只影偶的主路战斗，以便保留当前汤谷流程。
18. 作为玩家，我希望自由选择两条支路，以便探索不是完成主路的强制条件。
19. 作为玩家，我希望在安全且可达的位置按 F 阅读残碑，以便读取已批准的故事线索。
20. 作为玩家，我希望阅读时游戏时间冻结、F 或 Esc 可关闭，以便阅读不造成额外战斗风险。
21. 作为玩家，我希望满血时祭坛不消耗使用机会、受伤时仅成功恢复一次且封顶，以便回血规则明确。
22. 作为玩家，我希望栅门只能从内侧安全开启，画面与通行、阻箭同步改变，以便捷径行为符合预期。
23. 作为玩家，我希望三组战斗完成后仍能回头探索，以便没有遗漏的可选内容被强制关闭。
24. 作为玩家，我希望 R 同时重置战斗、探索、冷却与临时效果，以便每次重试从一致状态开始。
25. 作为玩家，我希望暂停、阅读、失焦和恢复不会粘键或补发旧攻击，以便可以安全中断操作。
26. 作为玩家，我希望窗口缩放和全屏切换后瞄准仍准确、人物不拉伸、HUD 可读，以便不同窗口比例均可游玩。
27. 作为玩家，我希望鼠标离开画面时取消待发攻击而保留正常移动语义，以便重返画面时不会自行续射。
28. 作为玩家，我希望跟随镜头保持现有视角与边界，以便看清人物、道路和危险范围。
29. 作为玩家，我希望人物上下身、弓箭、脚点与遮挡协调，以便保持已确认的皮影与像素质感。
30. 作为玩家，我希望在指定设备上获得已约定的帧率与稳定性，以便连续战斗没有明显卡死或效果残留。
31. 作为内容制作者，我希望在编辑器中查看并调整道路与障碍，以便不用修改战斗代码就能迭代通路。
32. 作为内容制作者，我希望在编辑器调整敌人出生点和互动点并马上试玩，以便快速检查可达性和战斗布局。
33. 作为内容制作者，我希望编辑后的布局在保存、重开和导出后保持一致，以便交付包真实反映我的修改。
34. 作为内容制作者，我希望复用现有图片、帧裁切和锚点信息，以便避免迁移造成不必要的美术返工。
35. 作为内容制作者，我希望缺失图片或非法裁切被明确指出，以便不会带着黑图或错误动作交付。
36. 作为验收者，我希望先实际试玩动态小样并确认画面与手感，以便在全图接入前发现方向性问题。
37. 作为维护者，我希望规则通过输入、时间推进和可观察状态验证，以便跨语言移植有明确对照。
38. 作为维护者，我希望现有行为用例逐项映射且已知缺陷单列，以便保留正确规则并避免机械复制错误。
39. 作为维护者，我希望固定旧版代码、资产与证据版本，以便能够还原参照并解释差异。
40. 作为维护者，我希望引擎、导出模板和依赖有锁定记录，以便在干净环境复现构建。
41. 作为验收者，我希望 Windows 和 Mac 的通过、失败与未测分别记录，以便单平台结果不会冒充双平台完成。
42. 作为维护者，我希望双平台验收通过后再切换主入口，并保留可还原参照，以便遇到发布阻断问题时能够定位与恢复。
43. 作为制作负责人，我希望早期明确 Steam 接入路径的兼容风险，以便后续发行准备有依据，同时不阻塞当前汤谷迁移。

## Implementation Decisions

### 技术与职责边界

- Godot 是已确认的后续引擎；采用原生二维世界、固定俯视／等距观感与离线图集。没有旋转镜头、真实高度交战或额外等距投影变换。
- 游戏脚本统一使用带类型的 GDScript。现有 TypeScript 规则与测试用于移植参照，Node.js 可用于制作和转换工具，不作为新游戏运行时依赖。
- 具体稳定版、匹配导出模板及渲染器在早期验证后锁定，保留版本与校验记录；初始评估 Compatibility，代表性材质或灯光不满足时再比较其他适合的渲染器。候选版本不能写成已经通过兼容验证的锁定版。
- 首期使用官方引擎与模板；引擎 fork、嵌入 JavaScript、双语言游戏运行时和通用 ECS 不属于本次方案。
- 战斗规则、输入适配、场景表现和桌面能力分别承担职责。规则决定移动、伤害、冷却和命中；表现层读取状态播放动作与效果，不通过动画回调再次裁决伤害。
- 初期保留既有几何与短时间步规则，避免同时替换物理、寻路和语言带来难以解释的行为变化；角色表现不与另一套物理运动裁决重复驱动。

### 对照基线与当前数值

- 在开始移植前固定可还原的当前代码、未提交改动、实际引用素材与数值参照，区分已确认行为、已知缺陷和未验项目。已有用户改动完整保留。
- 当前观察到的 64 项行为用例建立逐项映射；冻结基线时再次核对数量与实际行为。如果发现缺陷，记录预期修正与理由，不为满足逐帧相同而复制缺陷。
- 地图保持 2560×1440；三组分别 3／4／5 只影偶，共 12 只，三种外观沿用同一基础近战规则。主路、两条可选支路和内侧开启捷径均保留。
- 迁移期间不重新调平衡。当前参照包括玩家生命上限 100、普通移动速度 220、影偶生命 60 和近战伤害 20；普通箭伤害 15、穿透箭伤害 40、箭雨每段伤害 15，技能冷却和攻击时序按冻结基线保持。
- 现有受击流程自然产生的生命值以实际规则为准；祭坛恢复 40 且封顶，使用可自然形成的受伤状态验证，不通过修改血量制造截图。

### 战斗、探索与操作中断

- 保持普通射箭的短按、按住连射、前摇、恢复、冷却内不排队、离弦后弹道与最早接触规则。穿透箭每目标一次，实体阻断；箭雨固定落点、三段生效，合法性与消耗规则沿用参照。
- 保持闪避方向、位移、无敌窗、冷却和动作打断；长帧跨越前摇、挥击、闪避结束或投射物寿命边界时按实际经过时间推进，不能额外受伤、超射程或多结算一段。
- 保持敌人追击、绕障、预警与挥击阶段，所有正式出生点均能正常追击；外观不改变属性。
- 命中反馈区分敌人伤害与墙体火花，实际伤害、击退方向和反馈位置一致；同一事件重复呈现不重复播放，重试后旧事件清空，新事件仍可播放。反馈并发资源有界，不能随战斗时间无界增长。
- 互动选取当前附近、可达的最近合法对象，保持当前 80 世界单位距离规则，不隔墙、不因路过自动使用；按下沿触发，短点按不丢失，长按不重复。
- 已激活且存活的影偶禁止新开探索互动，未激活影偶不阻止安全互动；失败和普通暂停期间的输入不积压到恢复后。
- 残碑沿用已批准正文，可重复阅读；打开时冻结规则时间、取消待发攻击与残余闪避，保留冷却。F 或 Esc 关闭，阅读中 R 不重试；阅读叠加失焦时，关闭面板不能绕过失焦暂停。
- 祭坛满血不消耗，受伤时成功恢复一次 40 点并封顶到 100，成功后呈现已用状态。栅门仅内侧安全开启，保持现有开启过渡，通行与阻箭在生效时同步变化，直到重试前保持打开。
- 三组主路完成后允许回头探索。R 同时重置角色、遭遇、技能、投射物、反馈与探索状态；普通暂停和阅读中重试无效。重新启动不保留当前切片探索状态。
- 失焦触发暂停与操作中断；窗口变化取消操作意图但不因此暂停。鼠标离开取消待发攻击和相关输入，不清除仍合法的移动意图；返回时按住不自行续射。恢复后需要有效的新输入。
- 同一渲染帧或规则步之间发生的快速按下／松开仍应保留一次操作意图；技能和互动脉冲只消费一次，不在内部短步进重复触发。

### 空间、资产、表现与编辑器制作

- 二维世界单位保持一致，鼠标经当前相机变换转换到世界坐标后瞄准。镜头保持跟随、边界和现有缩放语义；全屏、超宽与最小窗口不能拉伸人物或改变世界命中位置。
- 角色根位置使用脚点，身体、弓箭、影子保持各自偏移；角色与物件按脚点及既定分层规则排序。大幅树冠、长墙和前景按实际遮挡需求拆分或处理，不能仅以开启排序作为验收依据。
- 复用既有实际引用的 PNG、帧裁切、方向、锚点和缩放信息；不同尺寸帧的脚点和握点必须保持，不能统一居中后丢失原始对齐。
- 资产转换可重复执行并追溯源内容；缺失图片、越界裁切、重复帧标识与非法数值明确失败，不能静默生成错误资源。配置与生成物的管理方式应支持干净环境复建。
- 布局定义与运行状态分离；生命、冷却、祭坛和门的可变状态不能通过共享定义资源污染其他对象或重试结果。
- Godot 布局资源在迁移验收后成为场景布局来源。用户可调整道路、障碍、出生点和互动点，保存、重开和试玩均使用修改后的布局，相关碰撞和可走范围同步更新；不长期维护两份互相冲突的布局真相。
- 用户负责编辑器调整与画面／手感验收，AI 负责脚本和批量配置。既有素材与构图作为参照，表现改进须记录用户确认。
- 使用真实可玩动态小样作为正式迁移的首个增量。小样包含移动、独立瞄准、普通射箭、一个影偶、一个遮挡物与跟随镜头；确认前不批量铺完整汤谷。小样代码和资产直接复用于完整切片，不另建抛弃式实现。

### 双平台交付与主入口切换

- 早期先导出双平台最小运行产物并在指定设备确认启动，再以纵向操作链推进到完整汤谷，尽早发现输入、渲染和资源组合问题。
- 最终交付 Windows x64 和 macOS arm64 可解压运行产物、版本与源码标识、产物校验、操作说明及每个平台的通过／失败／未测清单。具体封装随锁定的原生导出方式落地，运行包必须包含完整资源。
- 记录测试设备的系统、CPU／GPU、内存、显示刷新率、缩放和实际输出条件。未执行的 Windows／Mac 原生验证保持待验，交叉构建不代表运行通过。
- 迁移性能门槛为指定两平台实机 1080p 输出，预热后连续跑射 60 秒，平均帧率至少 58 FPS，至少 95% 帧间隔不超过 20ms；另做 5 分钟稳定性检查。保留逐帧数据、场景与输入条件、异常和资源趋势，不丢慢帧、不关闭正常敌人或效果来制造达标。
- 性能结论仅适用于记录中的设备与切片；不宣称商业版最低配置、最大敌人数或完整游戏容量。诊断指标可包括 CPU／GPU 帧时间、P95／P99、峰值内存、加载和包体，跨引擎对比须说明采样口径差异。
- 长时验收采用有明确设备、起止条件和停止原因的一次计划；遇到用户中止或前台条件无法成立时保留记录，不自行反复重启采样。
- 双平台原生功能、性能及画面／手感通过后再切主入口和开发说明，保留旧版可还原参照；发生发布阻断问题时允许临时回退入口并修复 Godot 版本，不自动撤销 Godot 方向。
- 本期只核实 Steam 接入路径、当前维护来源、许可及双平台兼容风险，记录已确认事实与待验证项。成就、云存档、Overlay、账号和商店分发不成为汤谷迁移运行依赖。

## Testing Decisions

### 已确认的三个测试边界

用户已确认以下边界，继续优先使用现有高层接口：

1. **规则边界：输入＋时间推进→可观察状态。** 验证移动、瞄准、碰撞、伤害、冷却、敌人、探索、反馈事件及重试；输入和布局可受控，断言面向玩家可观察结果，不测试私有方法或内部数组布局。
2. **操作中断边界：输入事件与窗口变化→输入适配结果和规则状态。** 验证快速点按、重复按键、离开画面、失焦、阅读、暂停、缩放及全屏，不为测试新增内部状态写入后门。
3. **原生体验边界：Windows／Mac 运行包→实际操作、画面与帧时间。** 验证真实输入、窗口生命周期、资源、遮挡、镜头、HUD、性能和稳定性。Headless、浏览器夹具或自动规则测试不能替代原生 GPU、窗口与实机确认。

### 自动化与既有用例

- 既有房间、汤谷战斗、探索、命中反馈、输入中断、镜头及路线测试提供迁移先例。冻结参照时核对已观察到的 64 项行为用例，逐项映射，不以新语言下相同函数名或相同测试数量作为等价证明。
- 相同输入序列、布局与时间步对比可观察结果；生命、伤害次数、命中去重、事件数量与阶段结果精确匹配，位置与角度采用明确记录且不改变玩法语义的浮点容差。
- 包含短时间步与长帧跨边界、同帧按下松开、暂停／失焦叠加阅读、重试后低序号事件重新播放、墙与关门阻挡、正式出生点可达等回归场景。
- 输入适配测试可以驱动受控事件；最终原生验收通过实际键鼠和窗口操作建立场景，不直接改血、清敌、传送、伪造焦点或跳过遭遇冒充通过。
- 只读验证资产转换后的有效引用与裁切；重复转换结果一致。编辑器修改通过保存、重开、试玩及导出行为验证，不用资源文件存在性代替实际可编辑。
- 自动检查应在干净环境完成资源／场景导入与解析、适用的脚本检查、行为测试和双平台导出；失败时返回可识别错误，不能仅依赖发行模式会移除的断言。

### 完成与证据边界

- 每项记录通过、失败或未测，绑定版本／源码标识、资源与产物校验、设备和必要截图／录屏。实际未验证的项目不能由构建成功推定通过。
- 用户先确认动态小样，最终再按完整切片和双平台结果确认画面与手感；两种确认分别记录。
- 平台入口、切换窗口、失焦和睡眠恢复按当前基线与目标设备实际验证；未取得的证据保留待验，不以注入状态替代。
- 本次指定实机性能目标是新迁移的验收合同；不追溯改写旧 MVP 的失败、未测或用户叫停记录。Windows 实机结果取得前保持平台验收开放。
- M0—M4 以当前切片和编辑器制作能力完成收束，不以未来正式肉鸽、存档或 Steam 功能尚未实现阻止收束。

## Out of Scope

- 手柄双摇杆、完整手柄菜单、按键重映射和断连重连的正式支持；其产品目标保留到后续商业闭环。
- 随机房间组合、多房间切换、Boss、技能树、装备、成长、奖励和新角色／新敌人机制。
- 一炷香、香火、借眼、签署、地区版本变化、正式神降结算、鼎成和其他主线／结局内容。
- 正式存档、房间结算点／战后检查点恢复、云冲突、旧玩家存档转换及事务恢复协议。既有切片探索随重试／重启复原。
- Steam SDK 完整集成、成就、云存档、Overlay、账号体系、Steam 商店发布或私有测试分支安装验收。
- 音乐、音效、配音和额外批量美术制作；现有素材的必要导入与对齐属于本期，新的表现改进仍需用户确认。
- 移动端、主机、Linux 原生、Steam Deck、Intel Mac、Windows ARM 的兼容承诺及商业版最低配置／容量承诺。
- 发行签名、公证、自动更新和商业渠道完整发布流程；首期需如实说明原生包实际运行条件和分发限制。
- 把旧版全部移入新物理／导航框架、引擎 fork、通用架构重构或与迁移无关的代码清理。
- 本次 to-spec 的代码迁移、安装引擎、生成美术、制作动态小样、执行原生长时采样、拆分发布实施票据、提交或推送代码。
