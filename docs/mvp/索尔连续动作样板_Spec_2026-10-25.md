# 索尔连续动作样板 Spec

日期：2026-10-25。状态：根据已确认 Q1—Q7 整理完成，待发布至 GitHub 并标记 `ready-for-agent`；尚未开始实现。（注：2026-10-29—11-05 期间优先推进了主角与怪物的[2/3 视觉缩放](商业深度肉鸽_人物缩放与单行技能栏_实施记录_2026-10-29.md)及主角[上下身连接、背面上身比例校准与背面行走八帧](商业深度肉鸽_人物连接与背面头部校准_实施记录_2026-10-30.md)；索尔本单方向连续动作样板仍保持待实施状态。）

## Problem Statement

玩家认为当前角色与 Boss 的整体移动、动作及衔接仍不够自然，反复调整后依然难以获得满意效果。索尔虽然已有拆件、距离驱动步态、脚部约束及三招动作，几何正确并不意味着承重可信、身体传力清楚或起停连贯；已有可编辑关节试点也仅覆盖待机与横锤，没有验证连续移动。

当前需要一段可重复比较、可编辑、由真实规则驱动的连续动作样板，验证制作路线是否有效。不能用更换插件、增加插值或通过后台断言代替动态效果确认，也不能通过改变移动响应与战斗时序取得视觉改善。

## Solution

先制作索尔单方向的独立候选，完整覆盖“迈步追近 → 停步承重 → 蓄力横锤 → 挥出 → 收招 → 再次迈步”。保持皮影形象与比例，以可信承重、骨盆至胸肩再到手臂与锤的动作传递为基础，在既有攻击时长内适度夸张。

以已有 Godot 原生拆件和 AnimationPlayer 关节试点制作可编辑片段，复用已有脚部约束。先调关键姿势与身体传力，再调曲线、相位和衔接；有证据证明素材不足时补必要局部素材。

交付与当前默认 Boss 同素材、同尺度、同规则轨迹的并排动态对照，支持正常速度、慢放、逐帧及脚点／锤路辅助显示。AI 负责制作、修改和验证，用户通过自然语言反馈并判断改善，无需手动绑骨或编辑关键帧。

候选保持独立，用户确认本次连续动作改善后才替换默认 Boss。原生画面、实际交互与性能按用户安排另验。样板通过后再决定其他招式、四向素材及玩家适配的实施批次。

## User Stories

1. 作为玩家，我希望索尔迈步时脚与地面接触协调，以便感到角色在行走而非滑行。
2. 作为玩家，我希望迈步时身体重心与支撑脚相互配合，以便索尔的体量具有可信重量。
3. 作为玩家，我希望索尔停止追近时自然承重，以便身体不会瞬间跳回固定站姿。
4. 作为玩家，我希望停步能连续进入横锤蓄力，以便移动与攻击看起来属于同一个身体。
5. 作为玩家，我希望蓄力姿势在既有预警时长内清楚可读，以便沿用现有战斗节奏判断威胁。
6. 作为玩家，我希望挥锤由骨盆、胸肩和手臂协调带动，以便感受到动作的力量传递。
7. 作为玩家，我希望持锤手与锤的连接在动作中稳定，以便不会看到脱手、穿插或明显错位。
8. 作为玩家，我希望挥击画面与既有攻击生效时刻对齐，以便画面与战斗结果一致。
9. 作为玩家，我希望挥击后有连续收势和承重，以便动作不会突然切换到待机。
10. 作为玩家，我希望收招后能够自然重新迈步，以便下一次追近不跳姿或突然换脚。
11. 作为玩家，我希望重复起停与连续动作不会继承错误姿势，以便长时间交战仍保持稳定观感。
12. 作为玩家，我希望现有移动速度、输入响应、碰撞与攻击时长保持一致，以便动作改进不会改变操作习惯或战斗难度。
13. 作为玩家，我希望暂停、死亡和重开正确中断或恢复动作，以便不会继续播放失效的挥击。
14. 作为用户，我希望保留已认可的皮影形象、比例与风格，以便动作改进保持角色身份连续。
15. 作为用户，我希望必要时能够补画局部拆件或握持姿势，以便源素材限制不会被无效的参数调整掩盖。
16. 作为用户，我希望看到原版本与候选在同一轨迹和时刻下的并排动态，以便准确判断变化来自哪里。
17. 作为用户，我希望以正常速度判断整体节奏，以便确认动作在游戏速度下是否自然。
18. 作为用户，我希望慢放、逐帧并查看脚点与锤路，以便指出具体滑步、跳变和握点问题。
19. 作为用户，我希望 AI 根据自然语言反馈修改可编辑片段，以便无需手动绑骨或拖动关节。
20. 作为用户，我希望候选在我确认改善前保持独立，以便继续使用现有默认 Boss。
21. 作为维护者，我希望制作数据、候选版本、素材来源与运行引用可追溯，以便后续修改与用户确认对应同一版本。
22. 作为维护者，我希望复用现有规则与测试入口验证连续动作和操作中断，以便避免另建一套战斗或测试体系。
23. 作为用户，我希望明确区分后台通过、离线动态确认和原生实机验收，以便了解本次结果实际覆盖哪些体验。
24. 作为维护者，我希望先用单方向样板验证路线，再评估四向和玩家适配，以便后续制作建立在已经验证的效果上。

## Implementation Decisions

- **职责边界**：战斗规则继续裁决移动、阶段、时间、伤害、碰撞、冷却、无敌与操作中断；呈现层只读取结果并采样动作，不通过动画完成信号、方法轨或帧号另行裁决战斗。
- **复用范围**：扩展已有原生拆件与可编辑关节片段候选，复用默认 Boss 已有的距离驱动步态和脚部约束。当前已有这些能力，不将其作为新框架重新开发。
- **动作范围**：本次只做单方向连续追近、停步、完整横锤、收势和再次迈步，并覆盖重复起停；其他招式与死亡表现沿用现有适用处理，不宣称已完成其新动作。
- **片段组织**：AnimationPlayer 保存可编辑姿势与时间曲线；移动衔接结合已有脚部接触约束。优先在现有候选内部完成，只有实际组合需求证明必要时才采用额外动画混合节点，不预建通用动画框架。
- **时间与相位**：采样依赖既有规则时间、动作阶段及实际地面位移；重复状态不额外推进，暂停不使用独立墙钟继续播放，重开不得继承上次动作。攻击片段与当前阶段时长一致。
- **接触与身体动作**：承重、重心和传力是关键姿势制作目标；脚部约束维持接触，握点维持持锤关系。约束不能取代动作设计，也不强制保留与新连续动作目标冲突的旧内部姿势结构。
- **形象与素材**：保留已认可的形象、比例和皮影风格。仅在记录具体限制后补必要局部素材，维护参考、修订、选择依据、正式来源、运行引用及验证证据。
- **公平对照**：固定旧版基线，旧版与候选使用相同素材、显示尺度、规则轨迹和采样时刻。若需补素材，先完成同素材的动作比较，再单独标注并比较素材修订，不能把混合变化全部归因于动画控制。
- **对照能力**：提供正常速度、慢放、逐帧和脚点／锤路辅助显示；离线合成明确标注来源与范围，不包装为引擎原生录像。无需为对照增加游戏正式 HUD 或新的玩法入口。
- **修改方式**：AI 负责片段、关节、必要局部素材、预览和验证，用户用自然语言反馈并评审；保留可重复编辑与重建所需的数据。
- **接入门槛**：候选独立；只有用户明确确认具体候选的连续动作改善后，才将获准的同一版本接入默认 Boss。接入后重新验证受影响的加载、流程和资源引用。
- **未通过处理**：定位具体姿势、脚点、素材或衔接问题，修订同一小样并重新对照；未获确认时保留默认版本与候选证据，不扩展其他方向或角色。
- **架构边界**：本次原生候选验证制作与运动衔接，不等同于全面采用运行时骨架；既有离线图集交付 ADR 保持有效。扩大骨架运行范围或改为烘焙图集，在样板结果明确后另作决定。

## Testing Decisions

### 已确认的测试边界

测试边界沿用访谈 Q1、Q6、Q7：以“真实规则输入／有效时间 → 公开状态 → 连续动作呈现与动态对照”为主要验收入口，复用既有 Boss 规则、输入适配和候选加载能力。暂停、死亡、重开等行为从该入口驱动，不新增仅为测试而存在的状态机或战斗裁决。

这是已有访谈中用户逐轮确认的边界，本次不另设访谈或改变验证范围。几何采样是辅助诊断，用户视觉判断与原生体验属于不同证据类别。

### 自动化行为验证

- 相同输入轨迹与时间推进下，对照规则公开状态，确认移动、攻击阶段、生效时刻、伤害、碰撞、冷却与无敌不因呈现改动改变。动画不能要求规则等待片段播完。
- 连续轨迹覆盖追近、停步、横锤全部阶段、收势、再次迈步及重复起停；重点采样阶段交界前后，而非只检查各片段中间姿势。
- 暂停期间及重复快照下，表现保持在相应状态；恢复后按规则继续，不积累额外墙钟进度。
- 挥击中死亡立即终止失效动作，采用现有死亡处理；不要求新增败退片段。
- 动作中重开恢复当前起始条件，结果与全新实例一致；真实失焦与其他操作中断沿用既有输入适配语义，不把全部中断都改成暂停。
- 同轨迹重放的脚点、握点与动作结果应可重复；支撑接触、连接稳定和不残留旧姿势可用可观察几何量辅助检查。容差依据现有坐标尺度和测试约定确定，不新设未确认的“自然度分数”。
- 不以内部节点名称、轨道数量或私有数据排布作为功能完成条件；既有骨长与锚点断言可以继续辅助定位，但不能代替外部行为与动态视觉验收。

### 现有测试先例与项目检查

- 规则／输入已有公开状态回归与真实操作中断适配检查，可复用其输入、时间和断言方式。
- 默认 Boss 动作候选已有真实规则驱动、关节端点及暂停采样检查；原生关节试点已有重复采样、重开、死亡与握点检查。扩展既有入口，避免另建测试框架。
- 修改 Godot 实现后执行项目统一后台检查；规则／输入按需运行既有无头 runner。资源与呈现变更按项目要求检查干净导入和对应原生包，并记录平台、版本、模式及实际结果。
- 本次 Spec 仅描述将执行的检查；历史测试数量和历史构建通过不作为新候选的通过证据。

### 动态与实机验收

- 正常速度下由用户确认移动有承重、整体节奏连贯、各阶段无明显跳变。
- 慢放与逐帧下检查脚地关系、身体传力、握点稳定、锤路以及攻击画面与现有生效时刻的对应。
- 每次比较记录旧版与候选版本、素材、尺度、规则轨迹和评审结论；明确区分用户确认与 AI 分析。
- 后台检查可证明规则、结构与加载；离线对照只证明相应合成表现，不覆盖原生过滤、最终遮挡、真实输入延迟或前台性能。
- 当前只在后台执行检查。用户安排前台后再验证原生视觉、交互与性能；Windows 实测继续按项目现有暂缓状态记录，不将导出成功视为 Windows 实机通过。

### 交付判定

独立候选具备完整连续动作、可重复编辑、动态对照与后台验证记录后，可提交用户视觉评审；此时只能声明“候选已交付”，不能声明“动作已通过”。

只有用户明确确认该候选的改善后，默认接入阶段才具备执行条件。接入状态、原生视觉、交互和性能分别报告，不以其中一项通过代替整体完成。

## Out of Scope

- 本轮不直接改造玩家，不将 Boss 拆件路线强制推广到玩家。
- 不在单方向样板通过前铺四向／八向、其他招式或其他角色。四向是后续目标，不是本轮交付数量。
- 不新增 Boss 战术决策、行为树、第三方动画运行库、自动识骨工具或通用动画编辑平台。
- 不更换引擎，不引入游戏运行时 AI，不要求用户手动编辑关节。
- 不改变移动速度、起停响应、伤害、攻击有效窗口、碰撞、冷却、无敌及现有操作中断规则。
- 不制作新败退动画，不借此扩展关卡、玩法、输入设备或剧情。
- 不将当前样板视为正式运行时骨架迁移，也不预先决定全角色烘焙方案。
- 不在用户安排前打开原生窗口、发送系统键鼠事件或进行前台性能采样。
