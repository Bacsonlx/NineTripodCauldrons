# 九鼎：首轮性能调优（后台逻辑层，2026-10-26）

本轮按 [`performance-optimization`](../../.agents/skills/performance-optimization/SKILL.md) 的「先定位瓶颈 → 只改主因 → 再测量」执行，配合 `godot-gdscript` 与 `godot-gdscript-headless-testing`。本次加载的技能与项目适配规则见 [Skills 使用指南](../guides/游戏开发Skills使用指南.md)。

## 1. 目标与边界

- 用户反馈低配电脑画面卡顿。沿用已确认门槛：1080p 连续跑射 60 秒平均 ≥58 FPS、至少 95% 帧间隔 ≤20ms，另做 5 分钟稳定性（[架构选型结论](九鼎_架构选型结论.md)）。
- 本轮只做**后台可验证的逻辑层优化**，保持规则、数值、碰撞、输入中断边界与已批准画面不变；Windows 实机与最终双平台验收状态不变。
- 本轮工作环境无法安装 `godot/engine-lock.json` 锁定的 4.7.2 引擎（下载重定向域名被网络策略阻断），因此**没有原生前后 FPS 数据**。本文不宣称性能已验收；所有实测数字须由目标机器产生。

## 2. 瓶颈定位（静态分析，优化前每帧代价）

| # | 位置 | 问题 |
|---|---|---|
| 1 | `combat/training_room.gd` `obstacles()` | 每次调用 `layout.obstacles.filter(...)` 新建数组。`can_walk_xy` 被移动、敌人寻路、视线、弹道接触、交互检测每帧调用上千次，等于上千次临时数组分配与障碍遍历。 |
| 2 | 同文件 `snapshot()` | `"interaction":nearest_interaction() if not nearest_interaction().is_empty() else null` 把昂贵的交互扫描做了**两次**；每次遍历障碍、探索点、药瓶并执行 `clear_path`。 |
| 3 | 全局调用链 | 一帧构造 4–5 份完整公开快照：相机 2 次（`update_camera`）、输入适配 2 次（`PlayerControls.update`）、流程 1 次（`RoomJourney.snapshot`）。每份深拷贝全部敌人、箭矢、特效、靶子。 |
| 4 | `presentation/training_scene.gd` 及三个子类 | `encounter_label.text` / `interaction_label.text` 一帧内被父子类重复写 2–3 次，每次触发中文字形整形与 CanvasItem 重绘。 |
| 5 | `world/environment_prop.gd`、`world/room_portal.gd` | 一个房间 100+ 个环境实例，每帧 `Sprite2D.to_local()`（内部每次求 `get_global_transform_with_canvas().affine_inverse()`）与 `get_rect()`，并重复写 `modulate.a`、`self_modulate`、门文字。 |
| 6 | `presentation/combat_effects.gd` | 最多 512 个半透明叠加精灵，每帧对每个重复写 `region_rect/rotation/z_index/visible`；帧末还遍历整个 512 池隐藏；`live_bursts`、`active` 等临时容器每帧新建。 |
| 7 | HUD / 拾取 / 特效 | 每帧格式化 `%d / 100` 字符串、解析 `Color("...")`、拼接 `drops + rewardPlaceholders` 临时数组；动作栏与怪物血条无条件 `queue_redraw()` / 改 StyleBox 颜色。 |

## 3. 本轮改动（等价替换，不改玩法）

| 模块 | 改动 |
|---|---|
| `combat/training_room.gd` | 障碍集合改为**按状态失效的只读缓存**（门开启、波次推进、房间完成时失效）；`journey_room.gd` 的封门改为 `extra_obstacles()` 钩子并入缓存；`snapshot()` 只扫描一次交互；新增 `player_point()` / `ui_paused()` 轻量查询与可开关的 `profile` 工作量计数器。 |
| `input/player_controls.gd` | 按键／指针／每帧状态判断改用轻量查询，`update()` 每帧只构造一次公开快照返回给相机、HUD 与特效共用。 |
| `journey/room_journey.gd` | `snapshot(base)` 可复用本帧快照（浅拷贝后只加流程字段），避免第二次深拷贝；`roomGraph` 仍每次新建，保持「外部修改图快照不污染真实状态」的既有约束。 |
| `presentation/training_scene.gd` | 相机读取 `player_point()`；`pose()` 按 `(图集, 帧号)` 缓存，帧未变时只写 `position`；HUD 文本收敛到 `hud_lines()` 虚方法，由 `apply_hud_lines()` 对 `encounter/interaction/status/fullscreen` 各写一次；三个子类只覆写文案字段。 |
| `presentation/first_level_scene.gd`、`room_journey_scene.gd`、`boss_scene.gd` | 原 `present()` 中的文本覆写迁到 `hud_lines()`；`room_journey_scene` 复用 `journey.snapshot(snapshot)` 的结果驱动掉落、小地图、Boss 血条与文本。 |
| `world/environment_prop.gd` | 缓存 sprite 的 `get_rect()` 与全局逆变换；用**每帧共享一次的画布逆变换**（`G^-1·(C^-1·p)`，与 `to_local` 等价）替代逐物件矩阵求逆；仅在值变化时写 `visible/modulate.a`；火焰闪烁量化到 20Hz（原信号约 0.8Hz，视觉不变）。 |
| `world/room_portal.gd` | 复用门框已缓存几何，缓存门文字与颜色，避免每帧 `get_rect()+to_local()` 与重复 Label 写入；漩涡动画与暂停冻结行为不变。 |
| `presentation/combat_effects.gd` | 复用 `burst_buffer` / `trail_active` 容器；缓存帧名、层级、角度，跳过未变的 RenderingServer 属性写入；常量化飘字颜色；帧末只隐藏上一帧实际使用过的精灵；新增可配置 `vfx_budget`（默认 512）。 |
| `presentation/combat_hud.gd`、`action_slot.gd`、`combat_overlay.gd`、`loot_view.gd` | 数值／冷却／血条颜色仅在变化时写入或重绘；拾取遍历不再拼接临时数组。 |

## 4. 低配机自适应（可选，默认不改变画面）

新增 `presentation/quality_policy.gd`：`--quality=high|medium|low|auto`。

- 默认 `high`（512 个特效叠加）＝已批准画面；**未显式指定时不会自动降级**，遵循表现改动须经用户确认的约束。
- `auto`：连续 90 帧 >22ms 降一档，连续 240 帧 <17.2ms 升一档，档位 512 → 256 → 96，带滞回避免抖动。
- 仅调整非玩法关键的特效叠加数量；不改碰撞、伤害、冷却、资源或规则时间。
- 启动：`./play --quality=auto`；原生包：`NineTripods.exe -- --quality=auto`。`--quality` 已加入 `PlayOptions` 白名单和 `play` 参数转发。

## 5. 后台工作量预算与测量

- `godot/tests/performance_checks.gd`（已纳入 `tools/migration/check_godot.py`）断言**确定性工作量**而非墙钟时间：
  - 2000 次可行走查询只重建 1 次障碍集合；
  - 单次快照只扫描 1 次交互目标；
  - 输入适配层在 300 帧密集战斗中每帧只构造 1 次公开快照；
  - 300 帧（8 波 × 6 影偶）内障碍重建 ≤20 次；
  - `RoomJourney.snapshot(base)` 不触发第二次规则快照，且外部修改关系图不污染真实状态；
  - 画质策略的降档／升档／默认保持 high 行为。
- 同机前后对比（**不是 FPS**）：
  ```sh
  python3 tools/migration/perf_godot.py --repeat 3
  ```
  输出 `ruleAndSnapshotUsecPerFrameMedian` 与工作量计数器。请在同版本引擎、同机器上先记录优化前基线，再记录优化后数值。
- 推荐在本机另外用 `godot --headless --path godot --script res://tests/run_tests.gd` 与 `python3 tools/migration/check_godot.py` 跑完整回归；55 场景／4250 次参照快照对比是行为等价的主要证据。

## 6. 后续（需原生测量后再决定）

1. **CPU/GPU 拆分**：在目标低配 PC 的 release 包上用 Debugger ▸ Profiler 与 Monitors 记录 `TIME_PROCESS`、`TIME_PHYSICS_PROCESS`、`RENDER_TOTAL_DRAW_CALLS_IN_FRAME`、帧时间分布。GPU 侧继续压叠加与过度绘制；CPU 侧继续压脚本与节点数量。
2. **呈现跟随渲染帧**：当前 `_physics_process` 即使显示只有 30 FPS 仍按 60Hz 跑全量呈现。若实测 CPU 仍超预算，可把 `present()` 节流到每个渲染帧一次（保持相机与瞄准同一计算步），这是下一轮最大潜在收益，但需重新复核相机／准星同步，不能与本次改动合并。
3. **预算固化**：目标机器取得基线后，把每子系统毫秒上限与 draw-call 上限写入本文件，并在 `check_godot.py` 中保留工作量断言防止回归。
4. 风格档位默认值、是否需要自动启用 `auto`、以及是否调整 1080p 门槛，须由用户试玩确认；本轮不擅自变更。

相关证据与实施状态见 [Godot 迁移实施记录](../migration/Godot迁移_实施记录.md)、[候选验收记录](../migration/Godot候选_验收记录.md)。
