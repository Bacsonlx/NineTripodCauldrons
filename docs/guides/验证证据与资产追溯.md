# 九鼎：验证证据与资产追溯

2026-10-23 起用于新任务及正在修改的记录。AI 按本指南分类报告验证，并在现有素材记录中维护参考、候选与交付关系。既有 Spec／ADR 决定验收门槛，本指南决定证据如何记录；历史日志保留原样，按需补索引。

## 验证证据

### AI 执行顺序

1. **开始任务时选检查。** 从下表选择与改动相关的类别，写明目标行为、入口、预期结果和当前可执行的检查。命令从根 [AGENTS.md](../../AGENTS.md) 与 [Godot README](../../godot/README.md) 读取。
2. **执行并保存证据。** 复用已有测试、重置、种子和公开状态；修复缺陷时尽量保留失败复现与修复后的结果。记录命令／操作、实际结果和证据文件。失败后修复并重跑受影响项，按项目要求完成全量检查。
3. **更新本任务记录。** 在对应 `docs/mvp/`／`docs/migration/` 的实施记录或当前 `output/` 证据 README 中使用下方模板；已有 JSON／日志继续作为明细，Markdown 只做索引。
4. **交付时按类别下结论。** 分别说明通过、失败、部分通过、未验证或不适用；未验证写明原因与下一项检查，不适用写明与本轮改动无关的原因。完成声明只覆盖已有证据支持的部分。

### 证据分类与结论边界

| 类别 | 能支持的结论 | 记录要点与边界 |
| --- | --- | --- |
| 构建／导入 | 代码可解析、资源可导入、指定平台可生成包 | 命令、退出码、引擎版本、包校验；导出 Windows 包不能写成 Windows 实机运行通过 |
| 逻辑／回归 | 给定输入和时间下，公开状态符合规则；修复后原错误未复现 | 用例、预期／实际、日志；节点、锚点、纹理或变换断言属于结构／逻辑证据，即使测试名含 visual 也不代表画面通过 |
| 运行／加载 | 指定工程或导出包在实际执行模式下加载到指定场景 | 平台、入口、是否 headless、到达状态、错误日志；无窗口加载只能证明后台运行边界 |
| 交互／流程 | 真实输入下，目标操作、进入／退出、暂停／失焦、失败／重开和相关流程可用 | 输入方式、路径、预期／实际、录制或观察记录；规则快照及脚本注入输入只覆盖对应自动化层，原生键鼠体验另列 |
| 视觉／表现 | 玩家实际看到的比例、可读性、遮挡、透明边、动作与 HUD 满足本轮要求 | 标明源图／浏览器预览／离线合成／Godot 原生截图或录像，记录分辨率、场景、动态状态和评审结论；静图不证明完整动作，源图不证明引擎呈现 |
| 性能／稳定性 | 在所记录设备、版本和场景中达到已确认指标 | 设备、系统／驱动、包、分辨率、预热、操作、时长、原始采样和阈值；后台帧率不作为前台性能，构建结果不推导性能 |

检查目的可以是冒烟、功能、缺陷回归、视觉或性能。**冒烟完成需要启动、到达可操作状态并执行主要输入；只有导入或启动时写“部分冒烟”。构建通过不等于试玩通过。** 一张截图或一次编辑器／MCP 操作也不能证明完整试玩。

项目当前只做后台检查；真实窗口、系统输入、前台性能按用户安排执行，Windows 实机仍暂缓。工具能力不足时运行当前支持的检查并保留待验项；无需为了截图把原生游戏改成 Web。视觉认可写明实际确认人和确认范围：用户选中母图或方向，不自动代表后续动作、接入画面或性能已确认。

### 本任务记录模板

复制到已有任务记录，删除占位文字并填写实际信息。所有相关类别都需有结论；纯文档任务只记录文档检查，游戏类别注明本轮不适用即可。

```markdown

- 对象与基线：任务／场景；提交 SHA，未提交工作树用源文件清单校验标识；引擎版本。
- 检查目的：功能／回归等；本轮目标、入口与预期结果。

| 类别 | 状态 | 平台／模式与实际结果 | 证据 | 未覆盖项／下一项检查 |
| --- | --- | --- | --- | --- |
| 构建／导入 | 填写 | 填写 | 日志或清单链接 | 填写 |
| 逻辑／回归 | 填写 | 填写 | 用例与结果链接 | 填写 |
| 运行／加载 | 填写 | 填写 | 日志链接 | 填写 |
| 交互／流程 | 填写 | 填写 | 操作与观察链接 | 填写 |
| 视觉／表现 | 填写 | 填写 | 预览类型、评审依据链接 | 填写 |
| 性能／稳定性 | 填写 | 填写 | 采样与设备记录链接 | 填写 |

警告与处置：列出实际 WARN／FAIL 及其影响、处理或保留原因。
交付结论：本轮已完成哪些工作，哪些验收仍待执行／确认。
```

来源与产物变化后重核受影响的结论。旧日志的通过状态属于当时基线；同名 ZIP 被重新导出后，用 SHA-256 区分版本。性能阈值与采样条件继续从对应 Spec／迁移方案读取，不在这里另定一套。

## 资产追溯

### 记录放在哪里

- 候选在现有 `output/art/<资产或任务标识>/<版本>/README.md` 记录来源和比较；使用已有资产编号，未登记资产先沿用任务目录标识。
- 交付后，以 `assets/<对应资产>/README.md` 为追溯入口，链接候选、决策、源文件、加工记录、Godot 使用位置和验证证据。项目已有 `asset-record.json`、提示词或哈希清单时直接链接。
- 资产中心继续管理现有编号、制作状态和预览；需要入口时在现有备注／制作记录中指向该 README。资产库的来源索引仍表示概念／需求出处，交付或视觉状态按各自实际证据记录。

### AI 执行顺序

1. **选参考。** 记录用途与规格依据，以及参考版本、路径和使用目的，区分“风格／文字上下文”“实际附入生成的图像”“直接加工的源文件”。只有实际调用附图时才能写成图像输入；缺失的模型、费用或授权信息写未知及原因。
2. **产候选。** 每版保留原图、完整提示词、实际工具路线、必要的源文件 SHA-256 与预览，写明从哪个版本派生、改了什么。复用现有资产合同中的尺寸、方向、锚点、层级和时序。
3. **记选择。** 分开记录用户明确决定和 AI 评审理由，附日期与可回查的确认记录。未获确认写待确认；未采用或退回的候选记录原因，保留文件。先接入后细调只代表获准接入，不等于最终视觉认可。
4. **记交付。** 指向正式源文件、运行资源、实际引用的脚本／场景／资源键、转换方式和证据。仅存在于磁盘或通过导出不算已在运行中使用；沿引用链核对加载入口，当前不可做原生检查时保留画面待验。
5. **修改后更新关系。** 修订候选使用新版本路径，记录替代谁、影响哪些运行引用及哪些证据需重做；未替换正式版本的候选写明未接入。查验时应能从运行资源倒查源图、候选与选定依据。

### 资产记录模板

放入候选或正式素材 README；同一节点可有多个参考，多候选可共用同一来源。

```markdown
## 参考、候选与交付（日期）

资产／任务标识：已有编号或任务标识。用途、规格与当前制作状态：填写。

| 关系 | 对象／版本（文件链接） | 依据或处理 | 确认与证据 |
| --- | --- | --- | --- |
| 参考 → 候选 | 填写两端 | 参考用途、是否实际附图／直接加工；提示词与工具记录链接 | 来源记录 |
| 候选 → 修订 | 填写两端 | 本次修正、保留与变更 | 比较预览与 QA |
| 候选 → 选择 | 候选版本 | AI 比较理由与未采用原因 | 用户决定或待确认；日期与记录链接 |
| 选定 → 交付 | 源文件与运行文件 | 加工方式、哈希、实际使用脚本／场景／资源键 | 加载／引用检查及验证记录 |

视觉确认范围与待验项：填写；更换源图／动作后的旧结论适用范围：填写。
```

需要画关系图时，可在同一 README 用 Mermaid 表达这些节点和箭头，文件链接表是可追溯的明细；无需新建第二份资产数据库。

### 已接入的真实示例

[皮影药囊 v1](../../assets/props/potion-pouches-v1/README.md#参考候选与交付)已按上述方式串联三组原型、用户选择 A、简化源图和 Godot 引用；同一 README 的[分类证据索引](../../assets/props/potion-pouches-v1/README.md#分类证据索引)展示如何分别记录后台通过与原生体验待验。它整理已有证据，本次没有重跑这些历史游戏检查。

## 可直接交给 AI 的任务示例

- “为这次功能修复选择相关检查，完成后按验证证据指南报告构建、逻辑、运行、交互、视觉和性能；当前仅后台验证。”
- “修订索尔横锤候选，按资产追溯指南记录实际输入、派生版本、修订理由和待确认项；正式版本是否替换按本次任务授权执行。”
- “接入已经选定的道具，补齐参考到交付的链接，并从运行引用倒查源图；原生视觉证据缺失时保留待验。”
